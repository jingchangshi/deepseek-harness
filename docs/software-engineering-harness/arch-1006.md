# DSH 通用 AI 编译器多 Agent 工程 Harness 泛化设计

## 1. 背景

当前 `deepseek-harness` 的 `ascendnpu-engineering-harness` 分支已经实现了一套较完整的多 Agent 软件工程工作流。其核心流程包括：

```text
Coordinator
    ↓
Scout Primary + Scout Secondary
    ↓
Architect
    ↓
Challenger
    ↓
Implementer
    ↓
Deterministic Verification
    ↓
Reviewer
    ↓
Acceptance
```

该系统同时具备：

- repository-owned task state；
- revision / workRevision；
- one-writer lease；
- bounded fix；
- explicit REPLAN；
- deterministic command verification；
- structured evidence；
- independent review；
- model output cannot directly mark task accepted；
- provider / role / data policy；
- interrupted-run recovery。

这些机制本质上并不依赖 AscendNPU-IR。

当前系统之所以表现为“AscendNPU-IR 专用”，主要原因并不是 Agent workflow 本身，而是 project configuration、verification policy、安装逻辑和部分 runtime 行为仍然携带 AscendNPU-IR 特定假设。

目标是将其改造成一个：

> **repository-independent AI compiler engineering harness**

使同一个 DSH engineering runtime 可以作用于：

```text
AscendNPU-IR
TileLang
Triton
LLVM / MLIR
IREE
XLA
TorchInductor
其他 AI compiler repository
```

而增加新仓库时，不再修改 harness TypeScript 核心源码。

TileLang 作为本次泛化工作的第一个真实 portability proof。

---

# 2. 当前架构中已经正确且应该保留的部分

以下能力已经具备较好的通用性，不应因为接入 TileLang 而重写。

## 2.1 Repository task protocol

当前：

```text
NEW
→ BASELINED
→ INVESTIGATED
→ PLAN_FROZEN
→ IMPLEMENTING
→ VERIFYING
→ VERIFIED
→ REVIEWING
→ REVIEWED
→ ACCEPTED
```

以及：

```text
REPLAN
BLOCKED
bounded fix
writer lease
CAS revision
atomic artifacts
```

均与具体 compiler 无关。

应保持：

> repository task state 是唯一工程状态权威来源。

DSH Session、Agent 对话和模型自述只能作为辅助信息，不能替代 repository artifact。

---

## 2.2 固定逻辑角色

当前角色：

```text
Coordinator
Scout Primary
Scout Secondary
Architect
Challenger
Implementer
Reviewer
Arbiter
```

已经足够覆盖 AI compiler 的分析、设计、实现与独立验证。

不应为 TileLang 增加：

```text
TileLangAgent
TVMAgent
CudaAgent
AscendAgent
```

未来也不应为 Triton 增加：

```text
TritonGPUAgent
LLVMAgent
MLIRAgent
```

正确模型是：

```text
Stable Role
+
Repository Context
+
Relevant Repository Skills
+
Current Task
```

即：

> 角色稳定，领域知识动态。

---

## 2.3 Deterministic verification

当前 harness 已经正确坚持：

```text
model reasoning
≠
verification evidence
```

Reviewer 即使说“实现正确”，只要 required deterministic command 没有 PASS，任务就不能 ACCEPT。

这一原则必须继续保持，并扩展到所有 repository。

# 6. 第一原则：Deployment 与 Repository 必须彻底分离

当前 `models.yaml` 同时被复制进入 target repository。

这不合理。

例如：

```text
Claude Opus → Architect / Reviewer
DeepSeek → Implementer
GLM → Challenger
GPT → Arbiter
```

属于用户的 multi-model deployment policy，并不是 TileLang 或 AscendNPU-IR 的 repository property。

因此应该拆为两类配置。

## User-owned deployment configuration

例如：

```text
~/.dsh/engineering/
    models.yaml
    roles.yaml
    data-policy.yaml
```

描述：

```text
provider
endpoint
model
reasoning effort
credential reference
role routing
```

## Repository-owned configuration

例如：

```text
<repository>/.agent/
    project.yaml
    profiles/
    adapters/
    runners/
    verification/
```

描述：

```text
这个 repository 如何构建
如何测试
有哪些 backend
哪些改动影响哪些 verification
哪些硬件能力可用
哪些 check 是 acceptance requirement
```

# 7. DSH profile 改为 repository-independent

用户只安装一次：

```text
engineering
engineering-run
```

之后：

```text
cd AscendNPU-IR
dsh engineering
```

或：

```text
cd tilelang
dsh engineering
```

或：

```text
cd triton
dsh engineering
```

Runtime 应从 Session cwd 动态解析：

```text
<cwd>/.agent/...
```

而不是在安装阶段固定：

```text
configRoot=/some/repository
```

因此：

```text
install runtime
```

和：

```text
initialize repository
```

必须成为两个概念。

---

# 8. Repository profile ID 必须动态化

当前 TypeScript、CLI 和 schema 多处写死：

```text
compiler
webapp
small-feature
```

例如：

```text
profile: 'compiler' | 'webapp' | 'small-feature'
```

以及 CLI enum validation。

这意味着新增：

```text
tilelang-compiler
triton-compiler
llvm-compiler
```

还需要修改 harness source。

这违反通用化目标。

应修改为：

```text
profile: string
```

并使用严格 ID grammar，例如：

```text
^[a-z0-9][a-z0-9-]*$
```

其是否合法由：

```text
.agent/profiles/<profile>.yaml
```

是否存在且 schema validation 成功决定。

核心 invariant：

> 新增 verification profile 不得要求修改 TypeScript enum。

---

# 9. Verification engine 不应理解 MLIR 特有概念

当前 compiler profile 中包含：

```text
ir-verify
ir-diff
dialect-legality
dominance-ssa
shape
alias-bufferization
```

对于 AscendNPU-IR 很合理，但并不是所有 AI compiler 的共性。

TileLang 是：

```text
Python DSL
→ TVM/TIRX
→ semantic verification
→ BackendContext
→ backend PassPipeline
→ host/device codegen
→ ExecutionBackend
→ Build / Load / Launch
```

因此 core verification engine 不应内置：

```text
dialect legality
dominance
bufferization
```

Core 只理解：

```text
check ID
category
required
scope
status
evidence
timeout
runner result
```

真正的 check name 应由 repository 定义。

---

# 10. Verification v2：Gate × Scope

当前 verification 的核心单位大致为：

```text
check name
```

但 AI compiler 往往是多 backend、多 target、多 mode。

TileLang 同时拥有：

```text
CUDA
ROCm
Metal
Ascend
LLVM
WebGPU
CuTeDSL
```

以及多个 execution backend：

```text
tvm_ffi
nvrtc
cython
torch
cutedsl
pto
```

因此 verification 的真正原子单位应该升级为：

```text
CheckInstance = Gate × Scope
```

例如：

```json
{
  "name": "source-codegen",
  "scope": {
    "targetBackend": "cuda",
    "executionBackend": "nvrtc",
    "hardware": "none"
  },
  "required": true,
  "status": "PASS"
}
```

另外：

```json
{
  "name": "runtime-correctness",
  "scope": {
    "targetBackend": "ascend",
    "hardware": "ascend950"
  },
  "required": false,
  "status": "NOT_RUN"
}
```

AscendNPU-IR 原来的：

```text
A3 / A5
PureAIV / MixCV
```

同样可以表示为 repository-specific scope value，而不是 core schema concept。

---

# 11. Deterministic impact policy

不能简单地：

```text
每个任务都跑完整 compiler regression
```

也不能让 Architect 自己决定：

> 我认为这些测试已经够了。

两种方式都不可取。

正确模型：

```text
Frozen Verification Set
=
Always Required Gates
∪
Deterministic Impact Rules
∪
Model Proposed Extra Checks
```

关键 invariant：

> 模型只能增加验证，不能删除 deterministic policy 要求的验证。

例如 TileLang：

```yaml
impactRules:

  - paths:
      - "tilelang/backend/**"
      - "src/backend/**"
    require:
      - backend-context-tests
      - source-lowering
      - native-build

  - paths:
      - "tilelang/analysis/**"
      - "src/transform/verify_*"
    require:
      - semantic-tests
      - valid-neighbor-tests
      - affected-lowering

  - paths:
      - "tilelang/ascend/**"
      - "src/ascend/**"
    require:
      - ascend-source-lowering
      - ascend-build
      - ascend-focused-tests
```

Triton 未来只需要提供另一套 rules。

Core 不修改。

---

# 12. Acceptance tier

多硬件 compiler 很难依靠一个简单：

```text
required: true / false
```

表示所有环境。

建议引入：

```text
development
presubmit
qualification
```

例如 TileLang Ascend backend。

## Development

要求：

```text
native build
source lowering
focused correctness
semantic regression
```

允许：

```text
Ascend device runtime = NOT_RUN
```

## Presubmit

增加：

```text
real Ascend runtime correctness
```

## Qualification

再增加：

```text
reference benchmark
performance regression
profiling
```

Acceptance tier 必须由：

```text
repository policy
或用户明确选择
```

决定。

Reviewer 不能临时降低 tier。

# 13. Runner 与 Command 必须分离

当前 Ascend adapter 中：

```text
怎么执行命令
```

和：

```text
要执行什么验证
```

混为一体。

例如：

```text
docker exec
→ bash
→ source environment
→ ninja
```

推荐抽象：

```text
Runner
  local
  docker
  ssh
  remote-device

Command
  pytest
  cmake
  ninja
  llvm-lit
  benchmark
```

例如：

```yaml
runners:
  local:
    kind: local

  ascend-build:
    kind: docker
    container: ...

commands:
  build:
    runner: ascend-build
    executable: ninja
    args:
      - ...
```

第一阶段至少实现：

```text
local
docker
```

接口预留：

```text
ssh
remote
```

---

# 14. Quiescence 必须成为 runner contract

当前 `automatic.ts` 会直接检测：

```text
executable == docker
```

然后针对 Docker timeout/cancellation 特殊进入 BLOCKED。

该 recovery policy 是合理的，但实现层级错误。

Core 不应知道 Docker。

Runner 应返回：

```text
quiescence = CONFIRMED
```

或者：

```text
quiescence = UNCERTAIN
```

automatic engine 只判断：

```text
UNCERTAIN
→ BLOCKED
→ explicit operator recovery
```

于是以后：

```text
Docker
SSH
remote NPU worker
Slurm
Kubernetes
```

都可以共享 recovery semantics。

# 15. Structured environment

当前 `CommandAdapter` 缺少正式 env schema。

TileLang Ascend 实际需要：

```text
USE_CUDA=OFF
USE_ASCEND=ON
ASCEND_HOME_PATH
ASCEND_TOOLKIT_HOME
LD_LIBRARY_PATH
```

不应该通过 arbitrary shell string 解决。

建议：

```yaml
env:
  set:
    USE_CUDA: "OFF"
    USE_ASCEND: "ON"

  inherit:
    - PATH
    - HOME
    - LD_LIBRARY_PATH
    - ASCEND_HOME_PATH
    - ASCEND_TOOLKIT_HOME
```

继续保持：

> no arbitrary shell parsing

# 16. Typed argv placeholders

当前只有：

```text
{{PROJECT_ROOT}}
```

未来建议支持：

```text
{{PROJECT_ROOT}}
{{BASE_REVISION}}
{{CHANGED_FILES}}
{{SELECTED_TESTS}}
```

必须使用 argv-level typed expansion。

例如：

```yaml
args:
  - -m
  - pytest
  - "{{SELECTED_TESTS}}"
```

展开为多个 argv：

```text
-m
pytest
testing/a.py
testing/b.py
```

不能变成 shell command string。

# 17. Repository-native knowledge

TileLang 已经包含大量高质量 repository skills：

```text
.agents/skills/tilelang-build
.agents/skills/tilelang-backend
.agents/skills/tilelang-semantic
.agents/skills/tilelang-layout
.agents/skills/tilelang-tvm-ir
.agents/skills/tilelang-ascend
...
```

这些信息不应复制到 DSH role persona。

Repository profile 可以声明：

```yaml
knowledge:
  instructionFiles:
    - CONTRIBUTING.md

  skillRoots:
    - .agents/skills
```

Runtime 向 Agent 提供：

```text
repository knowledge index
```

Agent 根据当前任务读取相关技能。

例如：

```text
修改 backend context
→ tilelang-backend
→ tilelang-build
```

而：

```text
修改数据竞争 verifier
→ tilelang-semantic
→ tilelang-tvm-ir
→ tilelang-build
```

这样实现：

```text
DSH = workflow intelligence

Repository skills = domain intelligence
```

# 18. Verification policy 也必须参与 revision identity

当前 `worktreeHash()` 排除 `.agent`，主要是为了避免：

```text
.agent/tasks/**
```

不断变化。

但是 `.agent` 中又存在：

```text
verification profile
adapter
project configuration
```

这会形成潜在漏洞：

```text
VERIFY 完成
↓
修改 verification policy
↓
source worktree hash 不变
↓
仍可能继续 REVIEW / ACCEPT
```

因此不应简单继续：

```text
exclude entire .agent
```

也不应该把整个 `.agent` 纳入 source hash。

建议拆分：

```text
sourceTreeDigest

verificationPolicyDigest

repositoryProfileDigest
```

PLAN、VERIFY、REVIEW、ACCEPT 必须绑定同一：

```text
workRevision
sourceTreeDigest
verificationPolicyDigest
repositoryProfileDigest
```

任一改变：

```text
→ REPLAN / REVERIFY
```

# 19. Freeze 也应拆层

当前 `.agent/FREEZE.json` 同时 freeze：

```text
runtime TypeScript
schemas
Ascend adapter
project config
compiler profile
```

这把：

```text
core runtime
```

和：

```text
repository preset
```

混为一体。

建议拆成：

```text
CORE_FREEZE
```

用于固定：

```text

state machine
repository engine
verification engine
runtime integration
schemas
```

而 repository preset 自己有：

```text
preset ID
preset version
preset digest
```

任务再记录：

```text
repositoryProfileDigest
```

# 23. TileLang verification strategy

TileLang 自身已经定义较明确的工程层次：

```text
Language Dialect
→ BackendContext
→ PassPipeline
→ Host/Device Codegen
→ ExecutionBackend
→ Build
→ Load
→ Launch
```

本地验证应优先从低成本、hardware-independent 层开始：

```text

```

之后才进入：

```text

ROCm execution

```

```text
task impact
+
acceptance tier
+
```

# 25. 核心架构 invariant

最终必须冻结以下 invariant。

## Invariant 1

新增 repository 不修改：

```text
automatic.ts
state-machine.ts
repository.ts
runtime/index.ts
verification engine
role protocol
```

---

## Invariant 2

新增 backend 不修改 generic harness。

---

## Invariant 3

模型不能降低 deterministic verification requirements。

---

## Invariant 4

Reviewer 不能覆盖：

```text
FAIL
NOT_RUN required gate
INCOMPLETE
missing evidence
```

---

## Invariant 5

Plan、Verify、Review、Accept 必须绑定：

```text
same work revision
same source state
same verification policy
```
