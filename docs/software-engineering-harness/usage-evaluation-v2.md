## Summary

This reference defines the `DESIGN_FROZEN` Phase 4 design for actual provider usage accounting and reproducible engineering evaluation. Design review is approved; implementation and verification have not started. Synthetic fixtures cannot establish model savings, and provider charges remain unknown unless a trusted deployment estimate is available.

<a id="actual-request-usage"></a>
## Actual request usage

Extend `TaskLifecycle` in `lifecycle.ts` so provider request settlement uses the request IDs already reserved before adapter dispatch. A reservation is `ADMITTED`; after adapter invocation it becomes `DISPATCHED` and receives a settlement. Persist exact start and end timestamps from the repository clock, outcome (`SUCCESS`, `FAILED`, `ABORTED`, or `INTERRUPTED`), and raw `TokenUsage` fields. A missing settlement, usage object, or authoritative total remains `UNKNOWN`; historical records never imply zero. Identical settlement for one request ID is idempotent, while conflicting settlement is rejected. Runtime settles every dispatched request, including failures and responses without usage. Only the owning lifecycle can settle branded request and attempt IDs.

`TaskLifecycle.settleProviderRequest(requestId, settlement)` records provider outcomes from `{ startedAt, endedAt, outcome, usage? }`; `usageReport()` returns the task report. `settleAttempt(attemptId, settlement)` records child outcomes after executor disposal and schema validation, using `SUCCESS`, `FAILED`, `CAPABILITY_INSUFFICIENT`, or `UNCERTAIN`. Attempt settlement cannot erase provider stream outcome; provider outcome and semantic role acceptance remain separate. An abort before adapter invocation becomes `ABORTED_BEFORE_DISPATCH` only with authoritative evidence that no invocation occurred, and contributes neither known usage nor the provider failure rate. A dispatched request with no post-dispatch settlement remains `UNKNOWN_DISPATCH` until late settlement or explicit recovery. It keeps usage and cost unknown and is counted separately from measured provider failures. SDK-internal retries are not separate requests because the adapter does not expose their dispatches. Compaction keeps a distinct request purpose. Session replay performs no provider dispatch and cannot charge the ledger again. Session usage events only link secondary reconciliation evidence through `requestId` and `sessionId`; they never settle missing adapter usage or create a second charge. A mismatch remains unknown and is retained for audit. Reporting reads do not mutate accounting.

Adapter normalization carries `cacheOmission: 'zero' | 'unsupported' | 'unknown'` separately from pricing. The pi-ai adapter declares `zero`, so omitted cache counters normalize to known zero; other adapters default to `unknown` unless they declare a category unsupported. A reported zero is known zero. Adapter-supplied `totalTokens` is the sole authoritative aggregate and is never reconstructed from component fields.

<a id="usage-reports-and-estimates"></a>
## Usage reports and estimates

Each usage row identifies task, workflow, role, provider, model, route, logical invocation, attempt, request, purpose, optional Session ID, raw usage, normalized totals, interval, outcome, and cost status. Reports aggregate physical requests, logical calls, attempts, failures, aborts, compactions, token totals, unknown-usage request counts, raw cache subtotals, and per-role/provider/model breakdowns. Total tokens are known only when every actual request has an authoritative `totalTokens`. Preserve input, output, cache-read, cache-write, and reasoning counts as raw fields; do not add cache counts to the provider total.

Report request-duration sum, provider-active time, and task end-to-end duration separately. Provider-active time is the union of settled request intervals; request-duration sum is their arithmetic sum. Persist `admittedAt` and terminal `finishedAt`. Lifecycle owns task timing: initial `RUNNING` admission and each recovery open a run interval; `BLOCKED` and `BUDGET_EXHAUSTED` close that interval without ending the task. A durable terminal transition writes `finishedAt` in the same state transaction. If the timing write fails, task duration stays `UNKNOWN`; recovery cannot synthesize a finish time during report generation. Cumulative end-to-end duration includes persisted run intervals and pauses. Never use an earlier blocked finish as the accepted completion time. Derive `wallTimeMs` from stored request timestamps; invalid intervals or a clock that moved backwards yield `UNKNOWN`, retain raw timestamps, and never produce a negative duration. Estimated charges remain separate from actual billed cost, which is `UNKNOWN` without invoice data.

Deployment pricing is optional and validated with `currency: 'USD'`, source, verification time, input/output rates per million tokens, optional cache-read/cache-write rates, and `inputAccounting: 'aggregate' | 'exclusive'` plus `cacheAccounting: 'reported' | 'not-supported'`. The request reservation stores a stable pricing version or digest so later configuration changes do not reprice history. Deployment metadata is an assertion, not independent verification of a provider's prices. Under aggregate input accounting, billable input is `inputTokens - cacheReadTokens - cacheWriteTokens`; a negative result or missing required term makes cost unknown. Under exclusive accounting, price input and each reported cache category separately. An omitted cache field is zero, unsupported, or unknown only as declared by adapter metadata; pricing cannot infer it. Missing rates, unsupported usage categories, invalid or future verification times, or inconsistent cache accounting yield `{ status: 'UNKNOWN' }` or reject configuration. Cost is `{ status: 'ESTIMATED', usd, pricingDigest }` only when supported usage and rates are complete; never label it actual billed cost. Use no live experiment prices unless official rates are verified. Never invent shipped prices. `maxKnownCostUsd` uses only configured estimates and fails closed when a request has unknown cost.

## Reproducible evaluation

The owner is `tools/agent/src/benchmark.ts`, with reviewed fixtures under `tools/agent/tests/fixtures/evaluation`. Keep this suite out of `benchmarks/`, whose performance gates do not permit network access. Four deployment-selected strategies use explicit route IDs: strong single agent (A), cheap single agent (B), fixed multi-agent (C), and adaptive V2 (D). For implementation fixtures, A and B each make one mutating implementation invocation, then use the same verifier and oracle; only their configured strong or cheap route differs. C always runs Scout, Architect, Challenger, Implementer, Verification, then Reviewer. D uses `runEngineeringTask`. For Review fixtures all strategies remain read-only: A and B make one reviewer invocation; C runs Scout, Architect, Challenger, Verification, then Reviewer; D uses `runEngineeringReview`. Every strategy receives the same named failure injection.

Four immutable Git fixtures cover a compiler feature/design task (`pebble-mul`, checked by `node tools/agent/tests/fixtures/evaluation/pebble/check.mjs`), an MLIR pass rewrite regression (`mlir-pass`, checked by pinned `mlir-opt` and a grammar oracle), a pinned Review task with introduced-bug and clean commits (`review-overflow`, requiring a finding path, SHA, and line), and deterministic failure recovery (`recovery-latch`, with first-attempt failure and final-source oracle). Each fixture fixes its seed Git SHA and source digest, request and criteria digest, command profile, oracle, allowed modifications, and execution/failure-injection manifest. The manifest includes classification policy and model routes with credentials removed. Oracles cannot accept model claims as evidence. Runs use isolated temporary repositories, deterministic setup, and awaited teardown. Every run records its seed and repetition.

`runEngineeringBenchmark({ cases, strategies, executor, oracle, now? })` returns an `OFFLINE_SYNTHETIC` or `LIVE_PROVIDER` report with conditions, case digest, strategies, results, and aggregates. Each result reports status (`ACCEPTED`, `REJECTED`, `BLOCKED`, `BUDGET_EXHAUSTED`, or `NOT_RUN`), `firstImplementationPass`, wall time, usage, provider failure rate, fallback and escalation counts, human-intervention count (`UNKNOWN` when unobserved), and oracle evidence. `firstImplementationPass` is the first implementation stage that satisfies the independent oracle before repair or retry; incomplete receipts make it `UNKNOWN`. Provider failure rate reports known failures over dispatched requests and separately reports `unknownDispatchCount`; an unknown dispatch is neither a measured failure nor a known success. Human-intervention counts require durable receipts; absent receipts mean `UNKNOWN`. Per-success tokens and cost include all effort in accepted runs, and become `UNKNOWN` if any contributing request is incomplete. Zero successes makes the metric undefined/`UNKNOWN`. Missing strategies and cases never count as passes. Negative controls for corrupted output, wrong source scope, fabricated review findings, and execution failures must fail the oracle.

<a id="execution-and-acceptance"></a>
## Execution and acceptance

Offline tests run production workflows with scripted roles and real Git/command oracles. Their token values are synthetic and cannot support model-savings claims. Live evaluation uses the supported `dsh` headless profile, an engineering repository overlay, and the real provider adapter, launched through `dsh --profile headless --patch <engineering-overlay> <request>` or the shipped `engineering-run` profile. Custom app launchers are not allowed. At least one available provider must persist nonzero raw usage and an outcome in the task ledger. When a provider is available, attempt all four strategies on at least one bounded fixture and report connection failures separately from accepted tasks or strategy comparisons. Live compiler, MLIR, and review cases may remain partial or `NOT_RUN` only with a recorded external, time, or resource limitation.

Keep raw provider logs and Sessions outside Git; publish only sanitized metadata and aggregate usage with unknown rates clearly identified. Phase 4 acceptance requires durable accounting, replay and recovery controls, independent oracles across all fixtures, accurate unknowns, and honest live-provider evidence. The design is frozen; Phase 4 remains unimplemented and unverified until those checks pass.
