# Agent Note: Degenerate output guard

Status: implemented

[English](2026-09-19-degenerate-output-guard.md) | 中文

## 问题

一个模型步骤可能在推理块内部塌缩成重复循环，耗尽整个单次请求的输出预算，却既不输出任何文本块，也不发起任何工具调用。该步骤随后以 `max-tokens` 结算，轮次结束，这一轮的全部工作丢失。

在同一个已记录会话（`session.v3.jsonl`，随报告附带）中的两次发生量化了该故障：

| 事件 | 轮次/步骤 | 推理字符数 | 行数 | 不同行数 | 输出 token |
|---|---|---|---|---|---|
| seq 704 | 2 / 122 | 480,942 | 47,267 | 129 | 128,000（上限） |
| seq 1546 | 4 / 48 | 326,793 | 30,066 | 142 | 85,195 |

两个块都是一个小短语循环重复到耗尽——`Let me write.` ×15,708、`Writing.` ×15,695、`Go.` ×7,856、`OK.` ×7,853。第一次事件的主导循环周期为 6 行，第二次为 4 行。

该塌缩是一个尖锐的相变，而非渐进衰减。在 seq 704 中，最后一段连贯推理结束于第 200 行（约 10,100 字符，约 2,500 token）；此后每个 5,000 行的窗口都恰好只含 4 个不同行。在 seq 1546 中，相变位于第 250 行（约 13,500 字符）。重复约占被烧掉预算的 97%，健康前缀只占其余部分。

该故障对现有的每一个守卫都不可见：`repeat-tool-reminder` 以 `(工具名, 规范化参数)` 为键，看不到一个不发起任何工具调用的步骤；`compaction-basic` 管理请求侧压力，从不检查实时输出；该步骤不产生文本，轮次在没有任何可续接内容的情况下关闭；`goal-round-driver` 将 `max-tokens` 视为停止条件并解除自动续接，因此 Goal 会话在人工执行 `/goal resume` 之前一直处于解除状态。

## 决策

`packages/guard/degenerate-output-guard` 监听实时助手流，按行结构评判一个尾部字符窗口，并在检测点取消生成，保留已流出的全部内容。检测与干预是两个独立阶段：`agent/assistant-stream` 监听器只做检测与取消；所有恢复决策都运行在 `turn/end` 处理器中，即被中止轮次落定之后、追加再次合法之时。

`onDetect` 的已发布档位是 `observe`（仅记录——基础组合包的灰度默认）、`abort-only`（取消，不跟进）与 `abort-and-continue`（取消，随后一条有界纠正跟进）。提案中的每轮 `maxInterventionsPerTurn` 变成了 `maxRecoveryAttempts`——作用于恢复链（输入为本守卫自身通知的连续轮次）的预算——因为纠正轮次是独立的一轮，每轮上限永远不会生效。`applyTo` 默认为 `reasoning` 而非 `both`：已记录的故障都是推理塌缩，而文本回答流携带合法的重复格式，需要单独校准。

## 检测

检测器（`src/detector.ts`）为每个被观察的块维护最后 `windowChars` 个字符的尾部窗口，加上待合并的增量尾部与计数器——状态由配置界定，与流长度无关，并按尝试与按块重置。评估摊销为每 `checkEveryChars` 个字符一次，外加块边界上的最终一次评估，因此只在最后一个不完整区间内才变得可疑的坍缩仍会被捕获。

一次评估将窗口切分为非空去空白行，跳过不足 `minWindowLines` 的窗口，并先计算不同行比例：高于 `distinctLineRatio` 即视为健康，不做周期扫描。否则在 `1..cyclePeriodMax` 范围内扫描周期 `p`，取最佳 `match(p) = |{i : lines[i] == lines[i-p]}| / (n - p)`；最佳比例达到 `cycleMatchRatio` 即触发并报告该周期。

与已记录会话的实测区分度很大：退化窗口的不同行比例为 0.0027–0.0047，而全部 308 个健康块为 0.4925–1.0000。以已发布阈值（4,000 字符窗口、`distinctLineRatio` 0.20、`cyclePeriodMax` 12、`cycleMatchRatio` 0.90）运行净化后的固定样本回放：两种已记录形态都在 20,000 字符前触发，健康语料零触发。

## 恢复链与关联

取消的 hook cause 内嵌检测 id——`degenerate-output-guard:<agentId>:<turn>/<block>/<charsSeen>`——`turn/end` 恢复只在落定原因与该 cause 精确匹配时消费 trip。关联按 cause 进行，而非按相邻性：被单独取消的轮次绝不会触发恢复，守卫从未见到开始帧的流尝试会被忽略。

恢复链在轮次领取的消息不是守卫自身通知（人类或驱动器轮次中断了链）时重置深度，只在守卫自身通知被领取时递增。被中止的 trip 在 `abort-and-continue` 下落定时，仅当深度低于 `maxRecoveryAttempts` 时才排队纠正通知；预算耗尽的链内再次退化仍会中止，但记录预算耗尽而不排队。按消息 id 跟踪的待处理通知若在被领取前被丢弃，则随丢失记录一并释放；同批搭乘的其他生产者消息不会破坏链。

## Goal 集成

当被中止的轮次属于已武装的 goal 轮次时，守卫在检测时快照 goal 的 id 与 revision。被中止轮次落定后，它重新武装 goal（以快照引用执行 disarm 加 resume），赶在 goal 驱动器的空闲暂停检查之前，因此守卫中止的轮次不会暂停 goal 自动化。对已武装 goal，纠正通知通过 `inject` 而非 `followup` 投递：消息停泊为下一步输入且不自带唤醒，goal 驱动器的待处理预约提供唤醒，通知搭乘下一轮批次。若检测与恢复之间 goal 状态漂移——不同的 goal、不同的 revision、非活跃阶段——恢复被跳过并记录，而非猜测。

## 投递时机

恢复工作运行在从 `turn/end` 监听器排队的微任务中。该微任务先于 agent 循环的空闲延续恢复运行，一次给出三项保证：追加合法（turn-end 发布已关闭）、goal 恢复赶在驱动器空闲暂停检查之前、排队的通知先于驱动器请求下一次 drive 存在。

## 配置

每个字段都是经校验的 `Config` 条目，并在 `apply` 中做失败即报的校验（非整数、越界数值与 `checkEveryChars > windowChars` 在加载时抛出）。生成的[配置目录](../../../../docs/config-catalog.zh.md#deepseek-aidsh-degenerate-output-guard)是字段与默认值的权威来源；包 README 记录面向操作者的契约。

## 已考虑的替代方案

**限制单次请求的输出预算。** 在路由上设置更小的 `maxTokens` 能限制每步的损害，但它不检测任何东西，并且会截断合法长输出。WorkBuddy 路由仍然完全不发送请求上限——`configuredMaxTokens` 只由 profile 声明的 `models[].maxTokens` 填充，而 catalog 中的 `maxTokens: 128000` 只是尺寸元数据，从不成为请求默认值——因此该上限仍值得作为纵深防御设置，而不是修复。

**降低 `reasoningEffort`。** 出故障的路由在模型自身声明默认值为 `high` 的情况下运行 `xhigh`，且 `onlyReasoning: true`、`canDisableThinking: false`。降低 effort 可能降低发生率，但它是概率性缓解，既无检测也无恢复。

**扩展 `repeat-tool-reminder`。** 该守卫的设计就是在 `tools/post-execute` 中观察到的精确重复工具调用；流级别的重复检测器与它不共享任何状态、事件或阈值。把二者合并到一个包中，只会让两种无关的检测共用一个配置面。

**响应 `max-tokens` 并自动续接。** 在整个预算花完之后恢复轮次，等于重新提示一个仍处于循环中的模型，续接会再次退化，而且它与 `goal-round-driver` 相冲突——后者在 `max-tokens` 上刻意解除。

**修改 `agent-loop` 以限制推理长度。** 在循环中为每步设置结构性推理预算，能预防而非响应该故障，但这是为模型行为问题改动循环，且需要为合法的长推理给出一个站得住脚的预算。流监听器接缝已经足够。

**在组装后的消息上检测，而非在流上。** 评估已结算的 `assistant/message` 无需逐 chunk 状态，但那时整个预算已经花完。尽早检测正是关键所在。

## 后果

- 被中止的退化步骤会把已流出的前缀留在历史中；守卫把保留的循环限制在检测点附近而非整个预算，且该前缀会作为 `thinking` 回放给提供方。
- 纠正通知是一条普通的已记录用户消息，因此"模型可见 ⟺ 已记录"规则无需新增会话事件即成立，客户端也通过既有的插件通知路径渲染它。
- 检测与恢复解耦：被守卫中止的 goal 轮次会重新武装其 goal，通知搭乘下一个 goal 轮次，因此 goal 自动化在一次坍缩后无需人工 `/goal resume` 即可延续。
- 守卫以 `observe` 档位、只观察 `reasoning` 块挂载在基础组合包中；切换到 `abort-and-continue` 并放宽 `applyTo` 是部署方在记录的检测给出依据后再做的决策。
- 每次尝试的状态由配置界定（窗口、待合并尾部、计数器）且仅存于内存；恢复的会话以空链状态开始。
- 阈值基于两次已记录事件校准；104 倍的区分度很宽，但来自单一模型路由的两个样本不足以确立其他路由上的误报率，这正是 `observe` 档位在强制执行前要度量的。
- 若模型每次尝试都退化，也会耗尽守卫的预算：`maxRecoveryAttempts` 对此加以限制，轮次随后以 aborted 结束，用户看到通知。
- 面向行的度量会漏掉没有行结构的退化：在行中间重复、或输出完全没有换行的循环，不会触发基于行的窗口。字符 n-gram 匹配可以覆盖它，但代价更高。

## 测试

检测器单元测试覆盖阈值边界（窗口大小、行数下限、去重比率健康、最佳周期选择、空增量与有界状态增长）。生命周期测试用脚本化适配器驱动检测、同步取消重入、单通知恢复、恢复预算、全部三个档位、两种块类型、按尝试重置、fiber 重挂载、配置校验，以及 goal 状态边界（缺失、解除、暂停、不可读、拒绝、漂移、丢弃、搭乘、投递失败）。Goal 集成测试在守卫旁边挂载 goal 服务与轮次驱动器，固定 goal 经中止的延续、预算耗尽的暂停、非 goal 轮次的恢复武装，以及被恢复通知的再次领取。两种已记录退化形态的净化固定样本回放都在 20,000 字符前触发；健康语料——密集分析、围栏代码、表格、CSV、测试向量、样板，以及重复但合法的页脚——从不触发。`pnpm run test:coverage` 在该包上保持逐文件 100%。
